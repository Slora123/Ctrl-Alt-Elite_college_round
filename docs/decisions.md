# Decisions and deferred items

## Decided

- **D-01 (P1) Location.** The P1 code lives in `core/` (package `crisisgrid_core`), a pure-Python project with no persistence, web or LLM imports (enforced by `core/tests/test_architecture.py`). The Node/Express website backend is kept as is for now; migrating it to the Python API is deferred to P4+.
- **D-03 (P1) Interactive runs are rejected, not filtered.** `verify_claim` raises `IneligibleRunError` if any offered `RunResult` is not a clean, verification-eligible run. `RunResult` itself refuses `verification_eligible=True` with `mode="interactive"`. The pseudo-code in system_design 5.2 filters silently; raising is stricter so caller bugs surface.
- **D-04 (P1) Claim comparison is in the claim's own unit.** The verifier compares `metrics[claim.metric]` to `reported_value` and `tolerance` directly. Percent vs fraction conversion is not guessed; a unit mismatch is the Audit rules' job (R-series) and reaches the verifier as `metric_mismatch` (verdict `inconclusive`).
- **D-05 (P1) Hashing.** Floats with integral values fold to ints (`1.0 == 1`); NaN/inf in a spec is an error. A bound cell's code is hashed via `ast.dump` (comments/whitespace ignored), with a comment/whitespace-stripping fallback for source containing notebook magics.
- **D-06 (P1) Edited-node provenance.** `create_version` sets edited nodes to `human` (author human) or `inferred` (author agent), per the Author-to-Provenance mapping.

## Deferred

- **D-02 Reconcile Paper Environment models.** `core.models` implements system_design 1.1 as written. `paper_env/paper_env/domain/models.py` already has local versions with extra fields (e.g. `Run`, `CellRun.blocked_action_id`, `Checkpoint.cell_versions`) and different shapes. They are not merged yet; decide in P5/P6 which is canonical and whether `paper_env` imports from `core`.
- **D-07 Attribution, Audit rules, Harness guard firewall test.** Not in P1. The firewall test lands with the first agent (P3).
- **D-08 `paper_env` persistence.** `paper_env` still uses `uuid4` hex IDs and SQLite; moving it to `uuid7` and the shared Postgres is deferred to the P5/P6 reconciliation (see D-02).
- **D-09 Rest of the monorepo skeleton.** P0 added `api/` (plumbing + FastAPI health) next to `core/` and `paper_env/`. `orchestration/`, `agents/`, `gateway/`, `worker/` are created in the phase that first needs them (P3, P4, P6) rather than as empty directories.
- **D-10 CI covers `core` and `api` only.** `paper_env` tests need `uv`, a jupyter kernel and network, and are not run in CI yet.
- **D-11 Docker Compose is untested.** `docker-compose.yml`, `api/Dockerfile` and the Postgres/pgvector branch of migration 0001 were written without Docker or Postgres available. Migration and health logic are tested on SQLite only. First thing to do when Docker is available: `docker compose up --build` and `curl localhost:8000/health` (expect `{"status":"ok","db":"ok","migration":"0003"}`).
- **D-12 Redis and MinIO are in Compose but unused** until P4 (streams/SSE) and P5/P6 (outputs, artifacts).
- **D-13 Package placement.** Instead of one top-level directory per plan component, pure logic lives in `core/` (Harness guard, later audit rules, route selector, verifier) and infrastructure-facing modules live in `api/crisisgrid_api/` as subpackages (`gateway/`, later `agents/`, `orchestration/`, `worker/`). Split into separate deployables when a process boundary actually exists (the worker, P6).
- **D-14 LLM access is behind `ModelClient`.** No provider keys were available, so tests use `ScriptedClient`. `gateway/litellm_client.py` (Qwen on Groq/Ollama, BYO keys) is written but has never been run against a real provider. Verify before relying on it.
- **D-15 Agents use a thin typed-output wrapper, not Pydantic AI.** `gateway/structured.run_structured` validates JSON against a Pydantic model with one guarded retry. Pydantic AI / pydantic-graph APIs change quickly and could not be checked against current docs here; swapping them in later only touches `gateway/` and `orchestration/`.
- **D-16 (P2) Audit rules R01-R11 are my definitions.** system_design.md only specifies R12-R16 ("R01 to R11 unchanged from v1", which was not provided). I defined: R01 seed, R02 hyperparameters (learning_rate, batch_size, epochs, optimizer), R03 split definition/provenance, R04 metric ambiguity (top-1/top-5, micro/macro), R05 compute, R06 code availability, R07 dataset availability (the only rule that emits `blocking`: private data), R08 dependency pinning, R09 variance/single run, R10 preprocessing, R11 pretrained weights. R06/R07/R15 map to the "Artifact Verification" page as in section 10. Replace with the v1 definitions if they differ. Text rules (R10-R14, R16) are regex heuristics that quote their evidence; they flag, never decide.
- **D-17 (P2) Embeddings are not in pgvector yet.** `ingest/embed.py` has an `Embedder` protocol, a deterministic hashing embedder and an in-memory index (used for context selection). A pgvector table and a real embedding provider (hosted vs local, open decision #5) are deferred; the migration already enables the `vector` extension on Postgres.
- **D-18 (P2) Gold-labelled parse evals not done.** Needs 3 real papers with hand-labelled values and a real model. The quote-verification step (`enforce_sources`) is the safety net in the meantime and is unit-tested. OCR fallback is a hook (`ocr=` callable); no OCR engine is bundled, a scanned PDF returns `needs_ocr=True`.
- **D-19 (P2) Artifact finder is rule-based, not an LLM agent,** and the GitHub adapter was tested against a mock transport only. Never run against the live API.
- **D-20 (P4) The pipeline is a small persisted state machine, not pydantic-graph** (see D-15). One method per node in `orchestration/pipeline.py`; state (`RunState`) is saved after every node and gates are DB rows, so a restart mid-wait loses nothing (tested: a second container on the same DB file resumes and makes no model calls). Harness-guard budgets and loop memory are per process and restart empty after a restart.
- **D-21 (P4) Nodes after Route are stubs.** Environment, Execute, Diagnose, Escalate, Verify and Attribute arrive with P6-P8. `reconstruct` records that no experiment ran and the run ends with an honest Tier-1 report; `GET /papers/{id}/claims` returns verdict `not_executed` for every claim. `edit_code` (stuck gate) and `action` gates are refused with a clear error until then.
- **D-22 (P4) API choices.** `POST /papers` takes the raw PDF bytes (no multipart dependency); URL ingest is not built. Pipeline work runs as a FastAPI background task and gate responses move the run to its next node synchronously, then continue in the background. PDFs are stored in the `papers` table for now (S3/MinIO later). Retrying the same failure at a stuck gate twice makes the guard stop offering `retry_with_hint`.
- **D-23 (P4) Reproducibility fixes found by tests.** Invalid model output is evicted from the deterministic cache (otherwise a retry would replay the same bad reply), the per-stage validation-retry counter resets per attempt, and claim ids are excluded from the gap auditor's prompt so an identical paper gives an identical, cacheable prompt.
- **D-24 (P6) The job queue is database-backed, not Redis streams.** `jobs`/`workers` tables with an atomic compare-and-set claim (`UPDATE ... WHERE status='queued'`), heartbeats on the worker row and a reaper (`JobService.reap`). Redis is still in docker-compose but unused. Retries follow the design: only infrastructure failures, bounded (default once); a failing cell, a timeout and a cancel are final. **The reaper is not scheduled yet:** `JobService.reap()` works and is tested, but nothing calls it periodically. Add a background task when the API runs as a long-lived process.
- **D-25 (P6) The worker is a lower-isolation subprocess runner and it says so.** `SubprocessNotebookExecutor` runs cells in a fresh `python -I` process with a scrubbed environment (no worker tokens or cloud credentials), a timeout, secret scrubbing of logs and errors, and kill-on-timeout. **It does NOT restrict network or filesystem access**, does not run as a separate user and sets no CPU/RAM limits: untrusted code can still read files the worker user can read. Docker (non-root, read-only image, limits, network allowlist, no host mounts) is not built; jobs can ask for `require_strong_isolation` and subprocess workers will refuse them. Reports carry a "lower-isolation worker" caveat. Do not point this at untrusted papers on a shared machine.
- **D-26 (P6) The notebook comes from the user, not from agents.** The Graph builder / Env builder / Code rebuilder are not built, so a clean run needs a notebook supplied with `POST /papers/{id}/runs {"notebook": <.ipynb>, "seeds": [...]}`. Cells publish numbers with `report_metric(name, value)`; names match claims ignoring case/punctuation. Notebook is not paper_env's notebook yet (see D-27). With no notebook nothing executes and the report says so. Case-3 runs get a "directional only" caveat; substitute data forces verdict `inconclusive` ("not a reproduction").
- **D-27 (P5 audit) `paper_env` status.** Against the 12-step list it implements most steps (notebook service with apply_edit/revert/stale propagation, uv env manager, dataset store, kernel runner, run modes, checkpoints, ComputeBackend, action hook, events + WebSocket/SSE, demo). Missing: `.ipynb` import/export, `!pip` rewrite (it only detects and warns), the Redis output stream, and a `KernelSession` record. **It cannot be imported on Windows (`fcntl`), so its tests could not be run here and no change was made to it.** A Linux CI job was added (non-blocking until verified). Integrating its KernelRunner as the worker's executor, and reconciling its domain models with `core` (D-02), is the next big integration.
- **D-28 (P6) No user authentication yet.** Only workers authenticate (bearer token, hash stored, registration closed outside `CG_ENV=dev` unless `CG_WORKER_REGISTRATION_TOKEN` is set). All user-facing endpoints (papers, runs, gates, jobs listing/cancel) are open. Add AuthN/Z before any shared deployment.
- **D-29 (P6) A run waits indefinitely for a worker.** If no worker has ever registered, jobs are queued and the run stays `waiting_jobs` (event `awaiting_worker`); there is no queue-wait timeout yet. If workers exist but none can run the job, a `stuck` gate opens instead.
- **D-30 (P8) Attribution and fidelity are built as pure functions but not wired into the pipeline.** `core/attribution.py` (direct vs one-at-a-time attribution, residual, 2-standard-error noise floor, partial results under a run budget, confound flags, `plan_single_runs`) and `core/report_check.py` (number post-check, agent-edit deviation list, reconstruction fidelity vs reproducibility) are tested, but nothing creates the inputs yet: graph versions are not persisted, no endpoint creates edited versions or runs one-at-a-time jobs, and `AttributeNode` does not exist. Version Comparison endpoints (`/graphs/*`) and PDF export are therefore not built; the report is Markdown only. Needs graph persistence plus the Graph builder (notebook cells bound to graph nodes) first.
- **D-31 (P8) Report writer is optional and fails soft.** With `PipelineDeps.narrative=True` the Report writer adds a short summary whose every number must exist in the evidence (checked inside validation; one retry naming the offending numbers, then escalate). If it cannot comply, the report is produced without a summary and says so in its caveats (it does not open a stuck gate, because every number is already stated in the deterministic verdict section). The default is off, so existing flows make no extra model call. Numbers are matched at the precision the text uses (91.3 matches 91.25; 90.9 does not match 90.8).
- **D-32 (P7) Repair loop is opt-in and conservative.** `PipelineDeps.repair=False` by default (a failed clean run goes straight to a human, as before). When on: the Run diagnoser classifies the failure, and the **Action hook decides from the diff itself** (it ignores the model's own risk claim). Only import/comment/path-only edits are applied automatically; anything touching hyperparameter-like tokens (snake_case, camelCase, numbers in paths) opens an `action` gate (approve / edit / reject) showing the diff. `infra` is retried not patched, `semantic` and `dependency` always go to a human (the diagnoser's fix is discarded), the same failure twice ends the loop ("repair gave up"), and agent edits always appear under "Deviations from the paper" in the report, even when a human approved them. The classifier is deliberately over-cautious (e.g. a path containing "cifar10" asks for approval).
- **D-33 (P7) Not built in P7:** package installs/pins during repair (the subprocess worker has no Env manager; a dependency diagnosis tells a human which packages to install), a revert endpoint (edits are an append-only history in the run state, so a revert would be a new edit), checkpoint-and-release while an `action` gate waits, and the whole notebook UI / approval inbox (frontend). The approval inbox is `GET /gates` + `POST /gates/{id}/respond`.
